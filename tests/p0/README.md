# P0 feasibility evidence

This directory contains feasibility tests for `PROJECT_PLAN.md` P0. The local component tests run in rootless Podman; `k3s-single-node-http.sh`, `topology-to-real-k3s-route.sh`, and `netbird-cross-host-udp-blocked.sh` also use isolated resources on the configured remote K3s cluster. Both the public VPS + separately NATed Docker host + topology-driven K3s route and the cross-host NetBird TCP/443 relay with UDP blocked now pass.

| P0 item | Evidence | Boundary |
| --- | --- | --- |
| Quarkus + PF4J lifecycle | `./mvnw -pl backend/panel-core -am test` dynamically builds and loads a provider JAR in a Quarkus test, then checks plugin task termination, PF4J loader closure, empty extension state, and weak-reference collection. | Does not implement Core plugin discovery policy, signature validation, or permission enforcement. |
| Rust Agent mTLS reconnect | `sh tests/p0/agent-mtls-nat-reconnect.sh` runs Agent in a separate rootless Podman `pasta` egress namespace, establishes an outbound mTLS gRPC stream to a host-only Gateway, restarts the Gateway, and checks that heartbeats resume on a second stream. | Exercises user-mode NAT-style egress and reconnect behavior; it does not use a public VPS or a remote customer NAT. |
| Agent → root Helper IPC | `sh tests/p0/helper-uds.sh` checks an authorized read of a root-owned fixture and rejects an unlisted capability, `../` traversal, a symlink escape, and a second UID. It also checks audit records. | Root is scoped to a rootless Podman user namespace; this does not prove host-root installation or authorization for system services, packages, or networking. |
| UDP-restricted overlay relay | `bash tests/p0/netbird-tcp443-relay.sh` starts pinned NetBird 0.75.1 peers and a self-hosted control plane behind loopback-published Caddy TLS. It blocks UDP on both peers' `eth0` ingress and egress, checks both peers report `Relayed`, and fetches an HTTP fixture across the overlay. The [ports and firewalls documentation](https://docs.netbird.io/about-netbird/ports-and-firewalls) describes the TCP/443 fallback. | Proves the relay path and peer traffic in one isolated rootless Podman network; it does not prove traversal across a public VPS, a separately NATed Docker host, or an external customer firewall. |
| Cross-host UDP-restricted NetBird relay | `bash tests/p0/netbird-cross-host-udp-blocked.sh` runs a temporary NetBird 0.75.1 control/relay endpoint behind the public VPS's Nginx TLS vhost, with one peer in the selected NAT container host (Docker or Podman) and a second peer beside an HTTP workload in `k3s-1`. It rejects UDP on both peers' `eth0` ingress and egress, checks both peer details report `Relay`, and fetches the K3s workload response over the overlay. | Uses `--resolve` and temporary host mappings to target the VPS IP without changing DNS. Proves TCP/443 control, signal, relay, and HTTP traffic across the tested VPS, NAT container host, and K3s; it does not prove DNS propagation or behavior behind unrelated customer firewalls. The script removes its containers, temporary vhost, namespace, and state. |
| Real single-node K3s Service | `sh tests/p0/k3s-single-node-http.sh` deploys a one-replica, resource-limited Nginx fixture into a unique namespace, reaches its ClusterIP Service through `kubectl port-forward` and SSH, then deletes the namespace. | Proves the selected K3s cluster serves HTTP; the SSH tunnel does not prove the public VPS, separate NAT Docker host, overlay relay, or topology-driven route path. Set `KEEP_NANPANEL_P0_K3S_ARTIFACTS=1` to retain the fixture namespace. |
| FRP import / diff / apply / verify / compensate | `sh tests/p0/frp-route-transaction.sh` imports the fixture, shows a one-port diff, runs official `frpc verify`, applies and restarts a pinned FRP 0.71.0 client, probes the new route, compensates, and proves the original route works again. | The Python helper is deliberately test-only and handles this controlled TOML subset. `plugins/provider-frp` is still a planned Provider. |
| React Flow → actual service route | `sh tests/p0/topology-to-frp-route.sh` starts a loopback-only P0 page and API plus isolated FRP, NAT-host-side client, and HTTP service containers. A Playwright test connects the Gateway, NAT Host, and Service nodes, saves the graph, applies the FRP configuration, and reads back HTTP 200 plus the active config hash. | This is an isolated lab adapter, not the regular authenticated console's topology API or a public/K3s deployment. |
| React Flow → public VPS → NAT Docker → real K3s Service | `bash tests/p0/topology-to-real-k3s-route.sh` creates a temporary NodePort fixture in `k3s-1`, confirms the NAT Docker host reaches it, then uses the saved React Flow Gateway → NAT Host → Service graph to apply and restart FRPC on that host. An external HTTPS request through the existing public Nginx and FRPS returns the fixture body and active config hash. | Uses `curl --resolve` to target the VPS public IP without changing DNS, a temporary exact-host Nginx vhost, and a temporary K3s namespace. Proves the FRP route and topology apply path; it does not prove DNS propagation or a cross-host NetBird relay with UDP blocked. The script removes its temporary resources. |

The FRP labs use pinned images by default: `ghcr.io/fatedier/frpc:v0.71.0`, `ghcr.io/fatedier/frps:v0.71.0`, and `docker.io/library/busybox:1.37.0`. Override them with `NANPANEL_P0_FRPC_IMAGE`, `NANPANEL_P0_FRPS_IMAGE`, and `NANPANEL_P0_HTTP_IMAGE` when testing a locally mirrored image. The NetBird lab also pins the server and peer to 0.75.1 and uses Caddy 2.10.2 for local TLS termination. Its host endpoint binds only to `127.0.0.1`; lab services communicate over a per-run Podman network. Scripts remove only the containers and network they created. Set `KEEP_NANPANEL_P0_ARTIFACTS=1` for Agent and FRP scripts to retain their temporary work directory and containers for inspection; `helper-uds.sh` always removes its single test container.

The real public HTTPS request and topology-driven FRP update to the K3s Service passed using `--resolve` for the selected VPS IP. The cross-host NetBird test also passed: both real peers report a relayed connection with UDP rejected on both `eth0` directions, and the NAT Docker peer fetched the K3s workload's unique HTTP body through the overlay. Together these results satisfy the P0 feasibility gate; the tests use controlled host mappings and do not claim DNS propagation or validation against arbitrary customer firewalls.
